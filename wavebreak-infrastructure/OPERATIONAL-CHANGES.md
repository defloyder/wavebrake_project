# Operational changes that live only on the server

Some production state on 45.15.41.3 (Istanbul) is not expressible as a
tracked file in this repo — either because it's generated at runtime, or
because it's host OS configuration outside any `wavebreak-infrastructure/`
path. This file is the record of what that state is and why, so it stops
being a surprise the next time someone (human or agent) looks for it.

## 1. Xray: PROXY protocol on the VLESS inbounds (2026-10-02)

**Where:** `/etc/xray/config.json` inside `wavebreak-pilot-xray`, in a
named Docker volume (`wavebreak_xray_config`) — not generated by
`xray/start-xray.sh` (that script only lays down a minimal single-inbound
bootstrap config the *first* time the volume is empty; this server passed
that point long ago, so the script is now a no-op pass-through and the
real config.json is maintained by hand).

**What:** `"acceptProxyProtocol": true` under `streamSettings.sockopt` for
the three inbounds reachable through nginx's shared port-443 stream proxy:
`vless-reality` (8443), `vless-xhttp-reality` (8445), `vless-direct-tls`
(18444). NOT set on `vless-cdn-ws` (2053, reached directly, no proxy in
front of it) or the internal `api` stats inbound (19999).

**Why:** nginx's `stream{}` block (see #2) terminates every public
connection on loopback before handing it to xray, so without this xray
saw every client as `127.0.0.1`. That made the connection-rate autoban
(#3) impossible and made "what's wrong for this one client" debugging
impossible too (see the Direct-TLS investigation that started this whole
chain of changes). This is the paired half of #2 — enabling one without
the other breaks every VLESS connection outright (confirmed the hard way:
see the incident note below).

**To reproduce after a volume loss:** pull the live config, patch the
three inbounds' `streamSettings.sockopt.acceptProxyProtocol`, validate
with `xray run -test -config`, `docker cp` back in, restart the container.

## 2. nginx: `proxy_protocol` on the stream listener + three backends (tracked, but the pairing matters)

**File:** `wavebreak-infrastructure/nginx/pilot-public-http.conf` (tracked
in git as of commit `3b3515a`) — `proxy_protocol on;` on the port-443
stream server, and `listen ... proxy_protocol;` + `set_real_ip_from
127.0.0.1;` + `real_ip_header proxy_protocol;` on the three backends it
reaches that nginx itself terminates TLS for: the website (18445) and
both API vhosts (18446 × 2, api/sub and core).

**Incident note:** deploying this file via `cp` into the compose
checkout and `nginx -s reload` is **not enough** — Docker bind-mounts a
*single file* by inode, and `cp` creates a new inode, so the running
container kept serving the old config while xray (already restarted with
`acceptProxyProtocol: true`) started rejecting every connection with
`proxy protocol signature not present`. All public VLESS traffic was down
for about a minute and a half until this was caught. **Fix/lesson:**
after replacing `pilot-public-http.conf`, always `docker restart
wavebreak-pilot-public-http` (not just `nginx -s reload`) so the bind
mount is re-resolved, and verify with
`docker exec wavebreak-pilot-public-http grep -c proxy_protocol
/etc/nginx/nginx.conf` before moving on.

## 3. UFW: connection-rate autoban on tcp/443 (host-only, not in any repo)

**File:** `/etc/ufw/before.rules` on the server (backed up before each
edit as `before.rules.bak-before-<reason>-<timestamp>`).

```
-A ufw-before-input -p tcp --dport 443 -m conntrack --ctstate NEW -m recent --name dpi_probe --set
-A ufw-before-input -p tcp --dport 443 -m conntrack --ctstate NEW -m recent --name dpi_probe --rcheck --seconds 60 --hitcount 20 -m limit --limit 10/min --limit-burst 5 -j LOG --log-prefix "[DPI-PROBE-BLOCK] " --log-level 4
-A ufw-before-input -p tcp --dport 443 -m conntrack --ctstate NEW -m recent --name dpi_probe --update --seconds 60 --hitcount 20 -j DROP
```

**Why this instead of banning on a failed-handshake log:** Xray's
REALITY/XHTTP-REALITY/direct-TLS inbounds deliberately run with
`"access": "none"` (see the earlier privacy-logging pass) — and REALITY's
whole security model is to say *nothing* when a probe doesn't present a
valid short ID, just transparently forward it to the camouflage dest. So
there is no content-level signal to key a ban on without breaking that
camouflage. What's left is pure TCP-layer shape: a real client opens one
connection and keeps it; active DPI probing (the RKN-style fingerprinting
this exists for) opens many, fast. 20+ new connections to 443 from one
source IP within 60 seconds triggers a drop that lasts until that source
stops tripping the window (self-expiring, not a permanent ban — a
legitimate client sharing carrier-grade NAT with noisy neighbors recovers
on its own within the minute instead of staying blocked).

**Tested live** (2026-10-02): a 25-request burst from a single source
started getting dropped at the 19th/20th attempt, and normal access
(`404` for an unmatched SNI) resumed within ~65 seconds unprompted, with
zero manual intervention.

**To reproduce after a server rebuild:** reapply the three lines above
into `ufw-before-input` (after the existing
`ctstate INVALID -> DROP` block) and `ufw reload`.

## 4. Monitoring: blocked-attacker count in the ops bot (2026-10-02)

`wavebreak-infrastructure/monitor/monitor.py`'s `dpi_blocked_snapshot()`
reads the `[DPI-PROBE-BLOCK]` kernel log lines from #3 via
`journalctl -k -g`, counts distinct source IPs over a rolling window
(default 24h), and the "📊 Мониторинг" screen in `bot.py` renders it. This
is tracked in git like the rest of the bot — the only reason it's listed
here is that it's meaningless without #3 already being live on the host.

**Deployed copy lives at** `/opt/wavebreak-monitor/` on the server (a
separate path from this repo's checkout — the checkout's
`wavebreak-infrastructure/monitor/` didn't exist on the server at all
before this pass; they're now byte-identical but still two different
paths, so future bot changes need the same manual
`scp` + `systemctl restart wavebreak-monitor` dance until that's
unified).

## Known gap: Hysteria2/UDP does not have any of this

Hysteria2's public UDP/443 is fronted by `cloak-relay` (a systemd service,
not a container — see `docs/CLOAK-TECHNICAL-OVERVIEW.md`), not by this
nginx stream block, so #1/#2 don't apply to it and its real-client-IP
visibility (or lack of it) hasn't been audited. A fail2ban-equivalent for
the UDP side is a separate task.
