# Промпт для агента: личный кабинет WAVEBREAK в мобильном и десктопном приложениях

Скопируй весь текст ниже и передай агенту вместе с исходниками мобильного и десктопного приложений.

---

Ты работаешь над мобильным и десктопным приложениями WAVEBREAK. Не создавай веб-кабинет: сайт `wavebreak.com.tr` является только публичной витриной и страницей загрузки. Весь клиентский кабинет должен жить внутри нативных приложений.

## Главная цель

Построй единый, завершённый клиентский сценарий внутри мобильного и десктопного приложения:

1. регистрация или вход;
2. безопасное хранение сессии и автоматическое обновление access token;
3. просмотр и выбор тарифа;
4. просмотр активной подписки и использования трафика;
5. получение и управление персональным подключением WAVEBREAK;
6. импорт собственной внешней ссылки подключения;
7. выбор профиля и подключение;
8. отображение текущего состояния, трафика и ошибок;
9. управление устройствами и выход из аккаунта.

Приложение рассчитано на два равноправных сценария:

- пользователь выбирает тариф WAVEBREAK и получает персональный профиль;
- пользователь добавляет собственную ссылку другого поставщика и использует приложение как универсальный клиент.

Нельзя прятать второй сценарий или делать его визуально второстепенной технической функцией.

## Перед началом работы

1. Изучи текущую архитектуру обоих приложений, модели, state management, навигацию, сервисы API и адаптер системного подключения.
2. Прочитай актуальные документы репозитория:
   - `docs/mobile-desktop-api.md`;
   - `docs/mobile-desktop-pilot-testing.md`;
   - `docs/vpn-config-contract.md`;
   - `docs/client-routing-policy.md`, если файл присутствует;
   - `AGENT_HANDOFF.md`.
3. Сверь каждый используемый endpoint с кодом `wavebreak-core`. Не придумывай маршруты, поля ответа или статусы.
4. Сначала составь таблицу: экран -> действие пользователя -> endpoint -> loading/empty/error/success state.
5. Сохрани существующий рабочий системный движок подключения. Не переписывай низкоуровневую часть без доказанной необходимости.

## Информационная архитектура

После авторизации используй компактную нижнюю навигацию на мобильном и эквивалентную боковую навигацию на десктопе:

- **Главная** — состояние подключения, выбранный профиль, основная кнопка включения, короткая статистика текущей сессии.
- **Профили** — профиль WAVEBREAK и импортированные пользователем ссылки.
- **Тариф** — текущая подписка, лимит, расход, срок действия, доступные тарифы.
- **Устройства** — список устройств, добавление, переименование и удаление в пределах API-контракта.
- **Настройки** — аккаунт, поведение подключения, диагностика, выход.

Не переноси административные функции в клиентское приложение. Управление узлами, пользователями, глобальными тарифами и инфраструктурой остаётся только в админке.

## Первый запуск

Первый экран должен сразу давать три понятных действия:

- `Войти`;
- `Создать аккаунт`;
- `Добавить свою ссылку`.

До авторизации разреши локальный импорт собственной ссылки, если текущая архитектура движка это поддерживает. После входа не удаляй локально добавленные профили: предложи сохранить их на устройстве рядом с профилем WAVEBREAK.

Не показывай длинный onboarding. Максимум три коротких экрана, которые можно пропустить.

## Главный экран

Главный экран не должен выглядеть как техническая панель. Обязательно покажи:

- выбранный профиль и локацию;
- состояния `Отключено`, `Подключение`, `Подключено`, `Переподключение`, `Ошибка`;
- одну крупную и однозначную кнопку включения;
- время текущей сессии;
- переданный и полученный трафик;
- короткое объяснение ошибки и действие для восстановления;
- явный индикатор, если устройство перешло между Wi-Fi и мобильной сетью.

При смене сети приложение должно попытаться восстановить соединение автоматически. Не заставляй пользователя вручную выключать и включать его после каждого перехода Wi-Fi/LTE.

## Профили

Раздели источники визуально, но не разными приложениями:

- `WAVEBREAK` — профиль, полученный через аккаунт и access grant;
- `Мои ссылки` — импортированные пользователем подписки и одиночные профили.

Для каждого профиля покажи название, источник, локацию, последнее обновление и состояние. Поддержи вставку из буфера, QR-код и системную передачу ссылки в приложение, если это допускает платформа.

Никогда не выводи секретные параметры профиля, refresh token или полный URL в логи и аналитику.

## Аккаунт и сессия

- Храни refresh token только в защищённом хранилище платформы.
- Access token держи в памяти или защищённом хранилище согласно существующей архитектуре.
- Реализуй один контролируемый refresh при `401`, без бесконечного цикла повторов.
- При окончательной ошибке refresh очисти сессию и покажи экран входа, не удаляя пользовательские локальные профили.
- Исключи повторную отправку операций покупки, создания grant и удаления устройства при сетевом retry.
- Валидацию полей показывай рядом с полем человеческим языком.

## Тариф и подключение WAVEBREAK

Покажи пользователю только понятные продуктовые данные:

- название тарифа;
- состояние;
- дата окончания или следующего списания, если API её возвращает;
- использованный и доступный трафик;
- допустимое число устройств;
- доступные локации.

После активации тарифа приложение должно получить access grant/config через документированный API, сохранить только необходимые данные и показать готовый профиль. Не заставляй пользователя копировать ссылку между экранами.

Поле `routing_policy`, возвращаемое backend, необходимо реально применять в конфигурации движка. Нельзя только распарсить и проигнорировать его. Частные сети и маршруты, отмеченные как direct, должны идти напрямую; остальной трафик — через выбранный защищённый профиль. DNS должен следовать выбранному маршруту. Реализацию обязательно подтвердить интеграционными тестами с фактической таблицей маршрутизации.

## Дизайн

- Используй официальный логотип и цвета из существующих ассетов WAVEBREAK.
- Интерфейс должен быть спокойным, тёмным и минималистичным, без огромных заголовков и декоративных карточек внутри карточек.
- Не копируй публичный сайт буквально: приложение является рабочим инструментом.
- Основные действия доступны большим пальцем на мобильном и с клавиатуры на десктопе.
- Для команд используй знакомые иконки с tooltip на десктопе.
- Для loading используй skeleton или локальный индикатор, не блокируй весь интерфейс без необходимости.
- Все экраны обязаны иметь loading, empty, offline, error и retry states.
- В публичном пользовательском тексте не используй запрещённую продуктовую терминологию. Пиши `защищённое подключение`, `профиль`, `сервер доступа`, `защищённая инфраструктура`.

## Диагностика

Добавь безопасный раздел диагностики:

- версия приложения и движка;
- платформа;
- состояние системного адаптера;
- выбранный профиль и транспорт без секретов;
- время последней синхронизации;
- кнопка проверки доступности API и точки подключения;
- экспорт обезличенного диагностического отчёта.

Не включай в отчёт токены, UUID персонального подключения, пароли, приватные ключи и полные subscription URL.

## Обязательная проверка

Проведи реальные integration/E2E сценарии на мобильной и десктопной платформах:

1. регистрация, вход, refresh и logout;
2. загрузка тарифов и активация тестового тарифа;
3. получение локаций и персонального профиля;
4. подключение и прохождение реального трафика;
5. переход Wi-Fi -> LTE -> Wi-Fi без ручного переподключения;
6. сон/пробуждение устройства и восстановление сессии;
7. импорт внешней ссылки, обновление и подключение;
8. недоступный API при уже сохранённом профиле;
9. истёкший токен и одновременные запросы;
10. отзыв access grant и корректное отключение;
11. отсутствие утечек DNS и применение `routing_policy`;
12. отсутствие секретов в логах.

## Результат работы

Не ограничивайся макетами. Реализуй рабочие экраны и подключи их к существующему API и системному движку. В конце предоставь:

- список изменённых файлов;
- карту экранов и endpoint’ов;
- результаты автоматических тестов;
- таблицу E2E-сценариев `PASSED / FAILED / BLOCKED`;
- список расхождений между документацией и фактическим API;
- отдельный список задач, которые объективно требуют изменений backend.

Не добавляй временные mock-ответы в production flow. Если endpoint отсутствует, зафиксируй блокировку и предложи точный контракт, но не маскируй отсутствие backend локальными фиктивными данными.
