# План: WAVEBREAK на микросервисах

Черновик 12.10.2026 для обсуждения владельца и коллеги. **Код и серверы не
трогались** — план, а не начатая работа. Переезд по частям, без остановки
сервиса; каждый шаг — после «ок» владельца.

## 0. Что есть сейчас

| Часть | Что делает | Где |
|---|---|---|
| **Core** (`wavebreak-api`) | один сервис ≈ 90 адресов `/v1`: вход и сессии, почта, сброс пароля, вход на ТВ по QR, Telegram-привязка; тарифы, подписки, промокоды; ключи доступа (grants), ссылки-подписки `/v1/sub`, «поделиться», устройства и лимиты; локации и ноды (enroll/heartbeat/usage/desired-state); весь админ-API; API для бота | `wavebreak-core` |
| `wavebreak-worker` | фоновые задачи: истечение подписок, отзыв ключей | `wavebreak-core/cmd` |
| `wavebreak-node` | агент на каждой ноде: тянет состояние у Core, правит Xray/Hysteria, шлёт трафик | `wavebreak-node` |
| Xray / Hysteria / edge (nginx) | данные пользователей, TLS, маршрутизация | `wavebreak-infrastructure` |
| Сайт, админка | Laravel; админка ходит в админ-API Core | `wavebreak-web`, `wavebreak-admin` |
| Бот мониторинга | Telegram, DPI-автобан | `wavebreak-infrastructure/monitor` |
| Данные | **одна** PostgreSQL (у коллеги на сервере начато отделение персональных данных — `pii.go`), Redis, RabbitMQ (есть, почти не используется) | docker compose на одном сервере |
| Клиенты | Android/TV, Windows (весь процесс с правами администратора), Lite, лаунчер | |

Что мешает уже сейчас: любая правка Core — пересборка и перезапуск **всего**
(вход, ссылки-подписки и ноды падают вместе); горячий путь `/v1/sub` и
ноды не масштабируются отдельно от админки; одна база — общая точка отказа;
серверный Core расходится с git (см. `PROJECT-STATE.md` п. 0, 0в).

## 1. Целевые сервисы

Не «по сервису на таблицу» — по зонам ответственности, которые меняются и
масштабируются независимо. Внешний API `/v1/...` для приложений **не
меняется**: его отдаёт шлюз, приложения ничего не замечают.

| Сервис | Отвечает за | Данные (владеет) | Сейчас в Core |
|---|---|---|---|
| **gateway** | единая точка входа: TLS, маршрутизация `/v1/*` по сервисам, проверка access-токена (JWT), лимиты частоты | — | edge nginx + middleware |
| **identity** | регистрация, вход, сессии и refresh-токены, почта и коды, сброс пароля, вход на ТВ по QR, Telegram-привязка, устройства пользователя | users, sessions, devices, ПД — **отдельная БД ПД** (то, что коллега начал) | `auth.go`, `device_login.go`, `me/*`, `devices` |
| **billing** | тарифы, подписки, промокоды, оплата (когда появится), истечение | plans, subscriptions, promo_* | `product.go` (часть), `promo`, worker |
| **access** | ключи доступа (grants), выдача конфигов, `/v1/sub` и «поделиться», лимит устройств по `x-hwid` | access_grants, share, hwid-устройства подписки | `me_access.go`, `share.go`, `sub_devices.go` |
| **fleet** | ноды и локации: enroll, heartbeat, желаемое состояние, учёт трафика, зеркала | nodes, locations, usage | `node*`, `relays`, `mirror_nodes` |
| **notify** | письма (Brevo), Telegram, будущие пуши — по событиям | очередь, шаблоны | `mailer`, бот |
| **admin-bff** | админ-API для админки: собирает данные из сервисов, аудит | audit | `admin*` |

Остаются как есть: агент ноды (говорит с **fleet**), Xray/Hysteria, сайт,
админка (говорит с **admin-bff**), бот мониторинга (читает **fleet**/**admin-bff**).

## 2. Как сервисы говорят

- **Синхронно** — HTTP/JSON внутри сети (как сейчас Core), каждый запрос с
  сервисным токеном; контракты — OpenAPI (`api/openapi.yaml` делится по
  сервисам) и контрактные тесты.
- **Асинхронно** — события через RabbitMQ (уже в составе):
  `user.registered`, `user.disabled`, `subscription.activated`,
  `subscription.expired`, `grant.issued`, `grant.revoked`, `device.removed`,
  `node.usage`. Пример: billing публикует `subscription.expired` → access
  отзывает ключи, fleet убирает их с нод, notify пишет письмо — вместо
  одного worker, который знает всё.
- **Авторизация** — identity выпускает JWT; gateway и сервисы проверяют его
  сами (общий публичный ключ), без похода в identity на каждый запрос.
- **Данные** — каждый сервис ходит только в свои таблицы. Сначала — отдельные
  схемы в той же PostgreSQL (дёшево, без новой инфраструктуры), физическое
  разделение — потом и только там, где нужно (ПД — сразу отдельно).

## 3. Порядок переезда («удушение» монолита, без простоя)

Каждый шаг: новый сервис рядом со старым → шлюз переключает его адреса →
неделя наблюдения → старый код удаляется. Откат — вернуть маршрут в шлюзе.

0. **Свести git с сервером** (обязательно до всего): Core коллеги (ПД, склейка
   устройств), 26+ коммитов `main` (31 конфликт), наш Core (промокоды,
   `install_id`, `x-hwid`, вход по QR, исправление «выкидывает со всех
   устройств»). Без этого любой сервис затрёт чужие правки.
1. **Модульный монолит.** Внутри Core разложить код по будущим сервисам
   (`internal/identity`, `billing`, `access`, `fleet`, `notify`, `admin`),
   запретить пакетам лезть в чужие таблицы (проверка в CI), события вместо
   прямых вызовов там, где это потом станет сетью. Деплой — тот же один
   контейнер. Самый важный шаг: дальше выделение — механическое.
2. **gateway**: edge nginx начинает маршрутизировать `/v1/*` по префиксам
   (пока все — в Core). Проверка JWT и лимиты — здесь.
3. **notify** — первый отдельный сервис: меньше всего риска (ошибка = письмо
   не ушло), подписан на события.
4. **fleet** — ноды и трафик: нагрузка растёт с числом нод, падение админки
   больше не трогает ноды.
5. **access** — горячий путь (`/v1/sub`, выдача конфигов): отдельно
   масштабируется и кэшируется, переживает перезапуски остальных.
6. **identity** вместе с БД ПД.
7. **billing** — когда появится оплата.
8. **admin-bff** — последним: админке всё равно, откуда данные.

## 4. Клиенты

- **Windows** (бриф `HANDOFF-pc-xray-migration.md`, фаза 2): интерфейс без
  прав администратора + маленькая служба Windows, которая держит TUN и
  движок (Xray/sing-box) и говорит с интерфейсом по named pipe. Права
  нужны только службе; обновление службы и движка — через лаунчер.
- **Лаунчер** — точка установки и обновления всех программ для Windows; в
  каталог добавляются новые сервисы (`wavebreak-launcher/catalog.go`).
- **Android/TV** — без изменений архитектуры (движок уже в отдельном
  процессе `:RunWaveEngine`); API для них не меняется — шлюз.

## 5. Что нужно для эксплуатации

- По контейнеру на сервис, общий шаблон (Go-сервис: конфиг, логи, метрики,
  `/healthz` — как в нынешнем Core).
- Трассировка запроса через шлюз и сервисы (request id уже есть в логах Core).
- CI: тесты и сборка каждого сервиса отдельно; выпуск сервиса не трогает
  остальные.
- Секреты — отдельно на сервис, не один `.env.pilot` на всё.
- Сначала всё на том же сервере (docker compose); второй сервер — когда
  понадобится масштаб или отказоустойчивость.

## 6. Риски и чего не делать

- Не дробить мельче шести-семи сервисов: на команду из двух человек каждый
  лишний сервис — лишний деплой и лишняя точка отказа.
- Не делить базу физически раньше времени — распределённые транзакции
  (подписка + ключи) сложнее, чем кажется; события + идемпотентность.
- Не начинать до шага 0: расхождение git и сервера уже стоило ошибок.

## 7. Оценка

Шаг 0 — 1–2 дня вместе с коллегой. Шаг 1 — около недели. Шаги 2–5 — по 2–4
дня каждый с наблюдением. 6–8 — по необходимости. Нужно решение владельца:
согласен ли с границами (раздел 1) и порядком (раздел 3), и кто ведёт шаг 0.
