# Обход белых списков: задание для коллеги (пункты 4 и 5)

Дата: 2026-10-02. Статус: задание на изучение и реализацию, кода пока нет.
Подробное исследование и источники: `docs/whitelist-bypass-research.md`.

Что у нас есть и чего не будет: российская виртуалка (Selectel, IP `135.*`, **не** в
белом списке) и турецкая виртуалка (наша нода). Ничего докупать не планируем.

## 0. Коротко: что такое белый список и почему текущие транспорты не помогают

Оператор мобильной связи в «режиме белых списков» пропускает только разрешённые адреса
(Яндекс, VK, госсервисы, банки, маркетплейсы). Всё остальное режется или «замораживается»
(соединение виснет после 15–20 КБ). Наши Direct+TLS и Hysteria+Cloak маскируют
**протокол**, но идут на **IP нашего сервера**. Если IP не разрешён, маскировка не помогает.

Есть два режима, их нужно различать:

| Режим | Что происходит | Что нужно |
|---|---|---|
| Шейпинг | Соединения с иностранными IP замирают, российские работают | Российский мост (пункт 4) |
| Жёсткий белый список | Работают только адреса из списка | Белый IP или туннель через разрешённый сервис (пункт 5) |

## Пункт 4. Российский мост (режим шейпинга)

### Идея

```text
Телефон  ->  РФ-виртуалка (Selectel, мост)  ->  турецкая виртуалка (выход)  ->  интернет
```

Телефон ходит на российский IP, и сессия не замерзает. Мост сам, по обычному интернету,
передаёт трафик на турецкую ноду. Участок мост -> Турция не попадает под мобильный фильтр.

### Что важно знать до начала

- Этот пункт работает **только в режиме шейпинга**. В режиме жёсткого списка IP
  Selectel `135.*` отрезается так же, как турецкий (в списке сообщества его нет).
- Проверка, нужен ли белый IP: поднять любой сервис на 443 на российской виртуалке и
  открыть его с телефона в мобильной сети без VPN. Не открылся — IP не белый.
- Сверка с публичным списком: в `cidrwhitelist.txt` из
  https://github.com/hxehex/russia-mobile-internet-whitelist нужен адрес/подсеть Selectel.
  Из Selectel там найден только `31.129.42.0/24` (по автоматическому разбору, проверьте глазами).

### Что сделать

1. **DNS.** Завести поддомен, например `ru.wavebreak.com.tr`, A-запись на IP российской
   виртуалки. Выпустить настоящий сертификат на него.
2. **Xray на РФ-виртуалке** версии не ниже 25.12.8 (по статье на Habr, более старые
   версии Reality детектируются). Вход: VLESS поверх WebSocket + TLS на 443.
3. **Исход на турецкую ноду.** Для первого прохода взять то, что уже работает:
   Direct VLESS WS+TLS (`direct.wavebreak.com.tr`, 443, путь `/wvb-dt`, см. `AGENT_HANDOFF.md`).
   REALITY на втором участке тоже возможен, XHTTP packet-up из статьи **не брать первым**:
   в `AGENT_HANDOFF.md` записано, что XHTTP ломал сессии Telegram, проверять отдельно.
4. **Маршрутизация на мосте:** российские домены напрямую (`geosite:category-ru`, `.ru`,
   `.su`, `.рф`), всё остальное в цепочку на Турцию. Это экономит трафик моста.
5. **Клиентские настройки** (из разобранного конфига конкурента): блокировать UDP на 443,
   чтобы QUIC уходил в TCP; блокировать BitTorrent; российские домены в `direct`.
6. **Файрвол на турецкой ноде:** принимать цепочку только с IP моста, чтобы турецкий IP
   не светился.
7. **Sysctl:** взять свой `wavebreak-infrastructure/sysctl/99-wavebreak-vpn.conf`.
   Агрессивные значения из статьи (`somaxconn=9000000`, `tcp_syncookies=0`) не копировать.

### Эскиз конфига моста (шаблон, значения подставить)

```json
{
  "inbounds": [{
    "tag": "from-client",
    "port": 443,
    "protocol": "vless",
    "settings": { "clients": [ { "id": "<UUID клиента>" } ], "decryption": "none" },
    "streamSettings": {
      "network": "ws",
      "security": "tls",
      "tlsSettings": { "certificates": [ { "certificateFile": "<crt>", "keyFile": "<key>" } ] },
      "wsSettings": { "path": "/wvb-br" }
    }
  }],
  "outbounds": [
    {
      "tag": "chain-to-tr",
      "protocol": "vless",
      "settings": { "vnext": [ { "address": "direct.wavebreak.com.tr", "port": 443,
        "users": [ { "id": "<UUID служебной учётки на TR>", "encryption": "none" } ] } ] },
      "streamSettings": {
        "network": "ws", "security": "tls",
        "tlsSettings": { "serverName": "direct.wavebreak.com.tr", "fingerprint": "chrome" },
        "wsSettings": { "path": "/wvb-dt" }
      }
    },
    { "tag": "direct", "protocol": "freedom" }
  ],
  "routing": {
    "domainStrategy": "IPIfNonMatch",
    "rules": [
      { "type": "field", "outboundTag": "direct",
        "domain": ["geosite:category-ru", "regexp:\\.ru$", "regexp:\\.su$"] },
      { "type": "field", "inboundTag": ["from-client"], "outboundTag": "chain-to-tr" }
    ]
  }
}
```

### Открытые вопросы, которые надо решить

- **Учёт трафика и пользователей.** В цепочке на TR приходит одна служебная учётка, а не
  grant каждого пользователя. Решение: учёт и проверка grants на мосте (`wavebreak-node`
  на РФ-виртуалке), либо отдельная схема передачи ID. Выбрать до интеграции в Core.
- **Интеграция в проект:** новый тип узла `relay` с `upstream` в Core, генерация цепочки в
  `wavebreak-node/internal/runtime/xray.go`, запись в `docs/vpn-config-contract.md`.
- **Юрисдикция:** сервер в РФ. Никаких логов пользователей, минимум данных на нём.

### Критерий готовности

С телефона в мобильной сети, где иностранные IP замораживаются, VPN через мост открывает
сайты и Telegram, держит несколько минут нагрузки, а трафик выходит с турецкого IP.

## Пункт 5. Туннель через разрешённые сервисы (VK, Яндекс Телемост, WB Stream)

### Идея

```text
Телефон -> звонок в VK / Телемост / WB Stream -> турецкая виртуалка -> интернет
```

Телефон «звонит» в сервис, который есть в белом списке (оператор видит только его IP).
Наша турецкая виртуалка заходит в тот же звонок вторым участником и выпускает трафик в сеть.
Внутри звонка идёт наш зашифрованный поток (SOCKS5/VLESS), сервис видит только данные звонка.
**Белый IP нам не нужен.** Это единственный вариант для жёсткого белого списка без белого адреса.

### План работ по этапам

1. **Оценка (1–2 дня).** Проверить лицензию `whitelist-bypass`. Развернуть сервер на
   турецкой виртуалке и клиент на Linux. Использовать **отдельный тестовый аккаунт VK**
   (не пользовательский). Замерить скорость и стабильность.
2. **Сервис на турецкой виртуалке.** Headless-создатель звонка (без браузера), запуск
   рядом с `wavebreak-node` в `docker-compose`, ключи и токены в секретах, не в репозитории.
3. **Клиентская библиотека.** Go-библиотека, собираемая через gomobile (в проекте уже есть
   `wavebreak-pc/native/hysteria_bridge` со сборкой AAR), даёт локальный SOCKS5/tun2socks.
4. **Core и клиенты.** Новый тип транспорта `carrier_tunnel`, по умолчанию выключен,
   показывать как «аварийный режим для белых списков». Выбор носителя: VK, Телемост,
   WB Stream, с автопереключением, если один не работает.
5. **Проверка.** На реальных SIM (МТС, МегаФон, Билайн, Tele2) в окно белого списка.

Носитель должен быть **сменным модулем**: если один сервис закроют или сломают, клиент
переходит на другой.

### Реальные ограничения

- **Скорость:** примерно 5–13 Мбит/с на туннель, задержки выше. Для мессенджеров, сайтов,
  лёгкого видео хватает, для тяжёлого стриминга нет.
- **Хрупкость:** изменение API звонка или лимитов ломает туннель. Нужна постоянная поддержка.
- **Условия использования:** платформы такое использование запрещают. Возможны баны
  аккаунтов и IP турецкой виртуалки. Нужны несколько одноразовых аккаунтов и план замены.
- **Детектирование:** синтетический трафик (VP8, DataChannel) может распознаваться,
  устойчивость к этому никто не измерял.
- **Платформы разные:** по README vk-turn-proxy, Телемост по схеме TURN там «закрыт»,
  но другие проекты его перечисляют как поддерживаемый. Статус проверять самим.
- Ozon: готового проекта не найдено, закладываться на него не надо.

### Критерий готовности

С телефона в жёсткий белый список (доступны только VK, Яндекс и т. п.) приложение через
выбранный носитель открывает сайт и Telegram, выход идёт с турецкого IP, скорость и
стабильность записаны по каждому оператору.

## Общие правила

- Секреты, UUID, ключи, токены и реальные ссылки подписок не класть в репозиторий и в чаты.
- Существующие два транспорта (Direct+TLS и Hysteria+Cloak) не менять. Новые транспорты
  добавлять отдельными записями в контракте конфига.
- Результаты тестов по операторам записывать в таблицу: оператор, регион, режим (шейпинг /
  белый список), транспорт, скорость, стабильность, дата.
