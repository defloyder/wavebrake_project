# Хендофф: переезд ПК-клиента на Xray-core — исследование готово, код НЕ начат

Это самодостаточный бриф для того, кто возьмётся за переделку Windows-клиента.
Не предполагает, что ты читал историю чата — всё нужное здесь. Собрано из
прямого чтения кода (`wavebreak-pc`, `wavebreak-mobile`), не из догадок.

**Статус: только исследование текущего состояния. Ни строчки нового кода ещё
не написано.** Фазы ниже — предложение, не обязательный маршрут; корректируй
по ходу дела.

## Зачем это вообще

ПК-клиент должен "летать всегда и везде" — быть максимально надёжным и
быстрым. Сейчас у него два структурных ограничения, которые тянут назад:
он не умеет часть реальных Xray-фич (нет XHTTP), и architecturally он не
по-настоящему process-separated (весь процесс запущен с UAC-элевацией вместо
узкого привилегированного хелпера).

## Что сейчас внутри ПК-клиента

Движок — **sing-box.exe**, отдельный дочерний процесс, запускается через
`Process.start` из `wavebreak-pc/lib/services/vpn/windows_vpn_adapter.dart`.
Конфиг для него генерируется на лету (`ShareLink.toSingBoxConfig()` в том же
файле) из распарсенной share-ссылки.

Поддерживаемые схемы: `vless`, `vmess`, `trojan`, `shadowsocks`, `hysteria2`.
REALITY работает (`tls.reality` блок + uTLS fingerprint, XTLS `flow` для
`vless` с `security=reality`) — через собственную реализацию sing-box, не
через настоящий Xray-core. TLS ClientHello фрагментация тоже уже есть
(`wavebreak-shared/wavebreak_links/lib/src/singbox.dart`, нативный
`fragment: true` в sing-box 1.12+).

**Чего не хватает**: XHTTP (sing-box его в принципе не реализует), gRPC-транспорт
не достроен в `ShareLink._transport()` (там только частный случай для `ws`,
комментарий говорит что grpc/httpupgrade "проходят насквозь", но по факту не
собраны). Это и есть прямая причина "переезжать на Xray" — не абстрактная
оптимизация, а конкретный пробел в поддерживаемых транспортах.

Отдельный сайдкар-процесс — **cloak-client-proxy.exe** (свой Go-бинарь,
собран из `wavebreak-shared/cloak/cmd/cloak-client-proxy`), сидит между
sing-box и реальным сервером на loopback для Hysteria2-ссылок с `cloak=1`,
потому что у sing-box нет cloak-awareness.

Упаковка — один Inno Setup инсталлятор (`windows/installer/wavebreak.iss`),
который кладёт `wavebreak.exe` + `sing-box.exe` + `wintun.dll` +
`cloak-client-proxy.exe` рядом (см. `windows/runtime_deps/README.md`).

## Тупик, который не надо заново открывать

В `wavebreak-pc/native/hysteria_bridge/` лежит `bridge.go`/`xray.go`/
`protect.go`/`tun2socks.go` — выглядит как заготовка Go-бриджа под Xray.
**Это мёртвый код.** По `docs/HANDOFF-cloak-pc.md` подтверждено, что это
наполовину скопированная заготовка, никогда не подключённая к сборке Windows
— там даже остался скрипт сборки Android AAR, который ссылается на
несуществующий под wavebreak-pc путь `android/app/libs/`. Игнорировать или
удалить, не достраивать поверх этого.

## Реальная цель переноса

В `wavebreak-mobile/native/hysteria_bridge/` (`bridge.go`, `xray.go`,
`protect.go`) лежит **рабочий** Go-модуль: встроенный Xray-core + клиент
apernet/hysteria в одном месте, собранный через gomobile под Android. Это и
есть то, что реально умеет XHTTP/Vision/REALITY по-честному — не
переупрощённая реализация sing-box.

Кросс-компиляция этого же Go-модуля под `windows/amd64` — реалистичный путь
получить настоящий Xray-core на ПК. Это не теория: `cloak-client-proxy.exe`
уже сегодня кросс-компилируется из общего Go-кода (`wavebreak-shared/cloak`)
под Windows — то есть тулчейн для "взять общий Go-код и собрать под Windows"
уже проверен в бою, просто ещё не применён к полному бриджу.

Mobile и PC сегодня **не шарят рантайм-код** — это две независимые реализации
движка. Перенос бриджа — это настоящая работа, не косметика.

## Микросервисный угол

Сейчас движок уже отдельный процесс (sing-box как child process) — это
частичный шаг к разделению. Но весь UI-процесс (`wavebreak.exe`) запущен с
полной UAC-элевацией, потому что sing-box'у нужны права на TUN-адаптер и
маршруты. Комментарий в `windows/runner/CMakeLists.txt` прямо называет это
временным компромиссом "until a privilege-separated helper service exists".

Целевая форма (описываю форму, не проектирую протокол — это на усмотрение
того, кто будет делать): UI-процесс без элевации; маленький привилегированный
хелпер-сервис владеет TUN-адаптером/маршрутами; Xray-бридж-бинарь общается с
этим хелпером. Как именно они говорят друг с другом (named pipe, local
socket, что-то ещё) — решать на месте, когда будешь в этом разбираться.

## Известные боли (попутно, раз уж будешь внутри)

- **Готовность после reconnect** определяется мэтчингом строки лога
  (`line.contains('sing-box started')`) вместо нормального сигнала готовности
  — хрупко.
- **Версии приложения** руками синхронизируются в двух разных местах
  (`pubspec.yaml` и `MyAppVersion` в `wavebreak.iss`) — уже были замечены
  разъезжающимися (`docs/HANDOFF-fragmentation-release.md`).
- **Нет OS-уровня эксклюзивности VPN на Windows** (в отличие от Android с его
  `VpnService.onRevoke()`) — вместо этого эвристика по именам сетевых
  адаптеров, чтобы заметить конкурирующий VPN.
- Сборка хрупкая: неэлевированный `flutter build windows` может молча
  собрать неполный бандл без `flutter_windows.dll`/`data/` — задокументировано
  в `windows/runtime_deps/README.md`, но это повторяющийся риск.

## Предлагаемые фазы (можно и нужно корректировать)

1. **Фаза 1** — кросс-компилировать мобильный Go-бридж под Windows, доказать,
   что он может заменить sing-box хотя бы для собственных грантов WaveBreak
   (REALITY/Vision). Сторонние (BYO) ссылки пока оставить на sing-box как
   фоллбек — разнообразие форматов чужих ссылок само по себе отдельная и
   немаленькая задача (см. отдельный список багов парсинга для мобилки).
2. **Фаза 2** — вынести привилегированную часть в отдельный
   хелпер-процесс/сервис, убрать элевацию всего приложения целиком.
3. **Фаза 3** — полностью убрать sing-box, когда покрытие BYO-ссылок на новом
   бридже подтверждено достаточным.

## С чего начинать

Прежде чем писать код: поднять ту же сборку бриджа, что уже работает для
`cloak-client-proxy.exe`, и попробовать скормить ей `windows/amd64` таргет на
простом тестовом конфиге (не прод-грант) — это самый быстрый способ понять,
есть ли в самом Go-модуле (`bridge.go`/`protect.go`) платформенно-специфичный
код (packet tunneling, routing), который не соберётся под Windows без правок,
до того как тратить время на остальную архитектуру.

## Статус 12.10 (app-main-sync) — фаза 1 начата

**Главное открытие: переносить мобильный мост не нужно.** Мобильный мост
(`bridge.go`/`protect.go`/`tun2socks.go`) завязан на Android: TUN приходит
дескриптором из `VpnService`, трафик в Xray заводит tun2socks, исходящие
сокеты выводятся из туннеля через `VpnService.protect`. На Windows этого
нет — зато в Xray-core той версии, что уже закреплена в мобильном
`go.mod` (26.9.9), есть свой **TUN-вход под Windows** (`proxy/tun`, Wintun):
- `autoSystemRoutingTable: ["0.0.0.0/0", "::/0"]` — Xray сам ставит и
  снимает маршруты;
- `autoOutboundsInterface: "auto"` — все исходящие сокеты Xray привязаны к
  физическому интерфейсу, петли через собственный TUN нет (то же, что
  `auto_route` + `auto_detect_interface` у sing-box);
- `dns` — DNS адаптера.

То есть ПК переезжает так же, как сейчас устроен sing-box: **отдельный
дочерний процесс `xray.exe` + Wintun**, только движок настоящий Xray
(XHTTP, Vision, REALITY — те же, что на телефоне).

Сделано (всё — только компиляция и разбор конфигов; на машине ничего не
запускалось, адаптеры не создавались):
1. `xray.exe` собирается под `windows/amd64` из той же версии Xray-core, что
   мобильный мост: `wavebreak-pc/native/xray/build.sh` (кладёт в
   `windows/runtime_deps/` вместе с `geoip.dat`/`geosite.dat`; не в git).
2. Генератор Windows-конфига — `V2RayURL.windowsTunConfiguration()` /
   `getWindowsTunConfiguration()` в общем `wavebreak_links/lib/src/xray_config.dart`:
   мобильный `fullConfiguration` (исходящие, DNS, умная маршрутизация,
   фрагментация ClientHello, mux для Direct-TLS — всё общее с телефоном) +
   вход `tun` (тег `in_proxy`, на него завязаны правила DNS умной
   маршрутизации) + `socks` на `127.0.0.1:<порт>` для проверки живости и
   пинга (как на Android).
3. Тест `wavebreak_links/test/windows_xray_config_test.dart`: при
   `XRAY_BIN=…\xray.exe` и `XRAY_LOCATION_ASSET=…\geodata` каждый конфиг
   прогоняется через `xray run -test` — 8 типов ссылок (REALITY+Vision,
   REALITY+XHTTP, Direct-TLS WS+mux, gRPC, VMess WS, Trojan, SS-2022,
   Hysteria2) × с умной маршрутизацией и без — **все 16 Xray принимает**.

Не сделано (следующие шаги фазы 1):
- `WindowsVpnAdapter`: второй движок рядом с sing-box за переключателем
  (по умолчанию sing-box) — запуск `xray.exe run -c`, готовность — по
  ответу SOCKS-пробы (а не по строке лога), проба/пинг через SOCKS
  `probe-in` (HTTP `generate_204`, как `measureTunnelLatencyMs` на
  Android), счётчики трафика — Xray stats API или статистика адаптера
  Windows (сейчас — Clash API sing-box), восстановление — перезапуск
  процесса (reload у Xray нет).
- CMake/Inno Setup: класть `xray.exe` + `.dat` рядом с `sing-box.exe`.
- **Проверка на живом ПК.** Владелец работает через Happ на машине сборки —
  запуск любого TUN там ломает ему сеть (12.10 так уже сломался Docker).
  Нужна отдельная машина/ВМ или окно, когда Happ выключен.
- Мёртвую заготовку `wavebreak-pc/native/hysteria_bridge/` не трогал:
  удаление файлов — после «ок» владельца.
- Фаза 2 (хелпер без элевации всего приложения) и фаза 3 (убрать
  sing-box) — без изменений.

### Обновление 12.10, вечер — движок Xray в приложении (бета, выключен по умолчанию)

- `wavebreak-pc/lib/services/vpn/windows_xray_adapter.dart` — `WindowsXrayAdapter`:
  `xray.exe run -c` (конфиг `windowsTunConfiguration`, адаптер `wavebreak-xray`),
  `XRAY_LOCATION_ASSET` = папка программы; готовность — по ответу пробы
  через SOCKS `127.0.0.1:47984` (HEAD `generate_204`, не строка лога);
  пинг — та же проба; трафик — метрики Xray `127.0.0.1:47985/debug/vars`
  (`stats.outbound.proxy`); проверка каждые 20 с, 3 провала подряд (если
  через proxy не шли данные), смена сети или падение процесса → перезапуск
  (reload у Xray нет), до 4 попыток.
- `windows_tunnel.dart` — `WindowsTunnel` (общий интерфейс для метрик и
  проверки трафика) и `WindowsEngineSwitch`: Xray получает подключение,
  только если включено «Настройки → Подключение → Движок Xray (бета)»,
  `xray.exe` лежит рядом с программой и Xray берёт ссылку как есть
  (`supports`: не cloak, не TUIC, не `allowInsecure`); иначе — прежний
  `WindowsVpnAdapter` (sing-box) без изменений. Переключатель выключен — всё
  как было.
- Умная маршрутизация на ПК (раньше её на ПК не было: sing-box не читает
  `routing_policy`): на Xray для своих локаций WAVEBREAK — как на Android,
  переключатель «умная маршрутизация» показывается на Windows при включённом
  Xray.
- Упаковка: `windows/runner/CMakeLists.txt` копирует `xray.exe`,
  `geoip.dat`, `geosite.dat` из `runtime_deps/`, если они есть (без них
  приложение собирается и остаётся на sing-box); `release.sh` собирает
  `xray.exe` скриптом `native/xray/build.sh`, если его нет. Пробная сборка
  Windows с ними прошла; установщик вырастет примерно на 60 МБ.
- Тесты: `wavebreak-pc/test/xray_engine_choice_test.dart` (какие ссылки идут
  на Xray), `wavebreak_links/test/windows_xray_config_test.dart` (конфиги со
  статистикой через `xray run -test`).
- **Не проверено вживую** (на машине сборки — Happ). Проверить на другом ПК:
